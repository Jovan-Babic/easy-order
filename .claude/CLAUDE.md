# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Easy Order is a multi-tenant B2B wholesale ordering system. A wholesaler ("client"/tenant) has users; its sales reps pick a customer, browse the product catalog, enter quantities/discounts and confirm an order that produces a shareable invoice. Serbian (`sr`) is the default UI language, English (`en`) the alternate.

Three projects live in this repo:
- `backend/` — FastAPI + MongoDB (motor), single file `server.py`, deployed to Vercel as a Python function. Also serves the Android APK and its update metadata.
- `frontend/` — Expo / React Native mobile app (Expo Router). Used by operators and admins; distributed as an APK built with EAS.
- `admin-web/` — Next.js 16 portal for superadmins and admins. Talks to the backend only server-side (route handlers proxy to FastAPI), so the browser never calls the backend directly.

End-user guides per role (Serbian, Markdown + screenshots, front matter `uloga` = role, meant to be shown in the app later) are in `docs/uputstva/` (`komercijalista.md`, `magacin.md` and `admin.md` done; screenshot tooling in `docs/uputstva/alati/`, run against a throwaway backend only). When a feature a role sees is added or changed, update that role's guide too (and re-shoot the affected screenshots). Project docs (Serbian) are in `.claude/DOCS/` (planned: `PLAN_JEDINICE_MERE.md` J3; later billing phases in `PLAN_NAPLATA_KALENDARSKA.md`): `IZMENE_BEZBEDNOST.md` and `IZMENE_RUNDA_2.md` (what changed and why), `RBAC_PLAN.md` (planned warehouse role), `SETUP_GUIDE.md`. The repo started on the "emergent" platform (`.emergent/`, old "Auto-generated changes" commits); that tooling is no longer used.

## Commands

### Backend (`backend/`)
```powershell
cd backend
pip install -r requirements-dev.txt   # requirements.txt = runtime only (what Vercel installs)
python -m uvicorn server:app --reload --host 0.0.0.0 --port 8000
```
API is under `/api`. Needs `MONGO_URL` and `DB_NAME` (from `backend/.env`). **`backend/.env` points at the real Atlas database** — don't run the test suite against it.

Tests are HTTP integration tests against a running server (they create real `TEST_*` records). Run them against a throwaway Mongo with demo data and no SMTP:
```powershell
$env:SEED_DEMO_DATA = "true"                          # demo client/admin/customers/products
$env:PASSWORD_RESET_DEBUG_TOKEN_IN_RESPONSE = "true"
$env:MONGO_URL = "mongodb://localhost:27017"; $env:DB_NAME = "easy_order_test"
# start uvicorn as above in another terminal, then:
$env:EXPO_PUBLIC_BACKEND_URL = "http://localhost:8000"
pytest tests -v
```
SMTP must NOT be configured for the test server: invites then return `temporary_password` in the response, which the tests rely on (`tests/helpers.py::activate_invited_user`). CI does exactly this (`.github/workflows/backend-tests.yml`, mongo:7 service) on every push touching `backend/`.

### Mobile app (`frontend/`)
```powershell
cd frontend
npm install    # runs scripts/cmd-guard.js --preinstall first (see below)
npm start      # expo start
npm run lint
npx tsc --noEmit
```
Production APKs and OTA updates are published by GitHub Actions workflows, not locally (see "Mobile app distribution" below).
`frontend/.env` needs `EXPO_PUBLIC_BACKEND_URL` (a phone can't reach `localhost` — use the LAN IP). Env vars are only inlined when written literally as `process.env.EXPO_PUBLIC_X`. Typed routes (`.expo/types/router.d.ts`) regenerate on `expo start`; a new screen gives tsc errors until then.

### Admin portal (`admin-web/`)
```powershell
cd admin-web
npm install
npm run dev     # needs BACKEND_URL and JWT_SECRET (same value as the backend)
npx tsc --noEmit
```

## Architecture

### Backend (`backend/server.py`)
- **Tenancy:** `customers`, `products`, `orders`, `users` carry `client_id`. `_scope_query()` / `get_scoped_or_404()` scope reads, `resolve_write_client_id()` scopes writes (superadmin must pass `client_id`). Cross-tenant access returns 404, not 403.
- **Roles:** `superadmin` (global, no client), `admin` (one client), `operator` (sales rep, creates orders), `warehouse` (processes orders; read-only for now). Dependencies: `get_current_user` (default for business routes), `require_roles(...)`, `require_manager` (= superadmin/admin; catalog/customer writes, deleting orders, image upload, user management), `require_order_creator` (superadmin/admin/operator). Admins manage only `ADMIN_MANAGEABLE_ROLES` (operator, warehouse) and edit themselves; assigning another role is 403. Operators see only their own orders (`_order_scope_query`; others 404). **Modules** (`Module`: `warehouse`, `stock`, `expiry`, `reports`; base is always on): `clients.modules` is edited by the superadmin only (missing field = all modules; `MODULE_REQUIRES` is validated), read on every request in `get_authenticated_user` (`User._modules`), gated with `require_module(...)` (403 `Module not enabled: x`, superadmin passes); fields of a missing module are ignored, not rejected, and data is never deleted. `/auth/me` + login return `modules`; portal `useHasModule`/`ModuleGate`/Sidebar and mobile `hasModule` (`src/utils/modules.ts`) hide the UI. Without `warehouse` an order is only `new`/`canceled`; stock is deducted on shipping only with `stock`. Plan: `.claude/DOCS/PLAN_MODULI.md`. **Subscriptions** (superadmin, portal `/subscriptions`): `plans` (name + modules) and `clients.subscription` (`plan_id`, `ends_at`, …) + append-only `subscription_events`; `subscription_state()` → `none` (no expiry) / `active` / `grace` (14 d) / `locked` (login 403 + tokens 401 "Subscription expired", superadmin unaffected). Assigning a plan sets `clients.modules` (a client on a plan can't edit modules directly). Daily `GET /api/internal/cron/subscriptions` (Vercel Cron, `Authorization: Bearer $CRON_SECRET`): reminder emails and, after 90 days locked, purge of stock data only (`_purge_module_data`) - deletes only with `AUTO_PURGE_ENABLED=true`, else reports `would_purge`; orders/customers/products/users are never auto-deleted. Plan: `.claude/DOCS/PLAN_PRETPLATE.md`. `GET /superadmin/overview` (superadmin: client/user/subscription counts + "needs attention" list) feeds the superadmin dashboard; the superadmin menu is Dashboard, Clients, Subscriptions, Users, App (business pages stay reachable by URL, just not in the menu). The superadmin client page (`components/ClientDetailTabs.tsx`) has tabs Overview / Users / Subscription (dialogs shared with `/subscriptions` in `components/SubscriptionDialogs.tsx`); `GET /users` rows carry `client_name` and `GET /clients` carries `user_count` (list only). **Payments** (superadmin, portal `/payments` + client tab "Payments"): `plans.prices` (months → RSD amount, optional) and `payments` (`status` `expected` = debt with `due_date` / `received` with `paid_at` / `canceled`, kept but never counted; `overdue` is computed). `POST /subscriptions/{id}/pay` and `/clients/{id}/charge-month` were removed with calendar billing; `POST /payments` for a client with a plan writes into its ledger (`_ledger_entry`: a debt becomes a numbered charge, money in a ledger payment). Dashboard shows received this month/year, total debt, overdue (`payment_overdue` in "needs attention"). **Superadmin tools:** `client_notes` (append-only, client tab "Notes"), activity (`users.last_login_at`/`last_seen_at` written at login and at most hourly in `get_authenticated_user`; `GET /clients` carries `last_activity_at`/`last_order_at`/`orders_30d`; `GET /clients/{id}/activity`), `GET /superadmin/system` (cron last run from `system_runs`, SMTP/Cloudinary/auto-purge flags), `audit_log` of superadmin actions via `_audit()` (`GET /audit`, portal `/audit`; `_log_subscription_event` also audits), and `announcements` (superadmin CRUD, portal `/announcements`; delivered in `/auth/me` as `announcements`, shown by portal `AnnouncementBanner` and mobile `TopBanners`). Plan: `.claude/DOCS/PLAN_SUPERADMIN.md`. `GET /orders` filters: `status` (repeatable), `created_by_user_id`, `from_date`/`to_date`, `limit`/`skip`.
- **Auth:** HS256 JWT with a `tv` (token_version) claim — bumped on password change/reset and role change, which invalidates older tokens. `get_authenticated_user` skips the first-login check and is used only by `/auth/me`, `/auth/logout`, `/auth/change-password`; everything else rejects users with `must_change_password` (403 "Password change required").
- **Accounts are created by invite:** `POST /clients` and `POST /users` generate a temporary password, email it (download link + portal link) and set `must_change_password`. If email fails, the response includes `temporary_password`. No endpoint accepts a creator-chosen password.
- **Passwords:** `ensure_strong_password` (8+ chars, a letter and a digit) — keep the client-side copies in sync (mobile/admin-web change- and reset-password screens).
- **Emails** are stored lowercase with a unique index (`normalize_email`, startup migration).
- **Rate limits** live in Mongo (`auth_attempts`, TTL): 5 failed logins per email per 15 min → 429; 3 forgot-password emails per email per hour (silent).
- **Orders are built server-side:** the client sends only `product_id`, `ordered_qty`, `discount` (must be in `product.discounts` or the default), `additional_discount` (must be in `product.additional_discounts`). The server snapshots name/price/VAT/packaging from the stored product into `OrderItem` — changing a product later never alters past orders. Orders also store `status` (`new → in_progress → shipped`, plus `rejected`/`canceled`; transitions via `POST /orders/{id}/status`, table in `_WAREHOUSE_FLOW`, admin/superadmin override needs a note, conditional update → 409), an embedded `status_history`, `created_by_user_id`, `created_by_name`. Warehouse packs via `PATCH /orders/{id}/items` (`picked_qty`, null = unchecked; first pick takes the order). Responses are `OrderOut` = order + `totals` (by `picked_qty` once shipped) + `ordered_totals` and per-item `line_net`, computed by `calc.py`. Invoice numbers are assigned on the first `shipped` transition (`_assign_invoice_number`): per-client `counters` doc (`invoice:{client_id}`, atomic `$inc`) → `PREFIX/0001`, or typed by the warehouse (`invoice_number` in the status body) when the client's `invoice_numbering` is `manual` (unique per client). The number never changes after the first shipment. While `new`, the creator (or an admin) can edit customer/lines with `PUT /orders/{id}` (re-snapshots prices; 409 once the warehouse took it). On `shipped`/`rejected` the order's creator gets an email (`_send_order_status_email`, best effort, skipped if they did it themselves or SMTP is off). `GET /reports/orders` (manager; counts per status, sales rep and warehouse handler for a date range) feeds the portal `/reports` page. Client invoice settings (`invoice_prefix`, `invoice_numbering`, `invoice_next_seq`, `logo`, `registration_number`, `bank_account`) are edited by the superadmin only; everyone reads their own via `GET /clients/me`. Logo upload: `POST /upload-image?kind=client_logo` (superadmin, folder `easy-order/clients`).
- **Package accounts & charges** (prepaid; plan: `.claude/DOCS/PLAN_SUPERADMIN.md`, proposal: `PREDLOG_NAPLATE.pdf`): `plans.included_seats` (role → accounts, missing = unlimited) and `plans.seat_prices` (monthly price of an extra account); `clients.subscription.extra_seats` (role → contracted extra accounts) and `discount_percent`, set by the superadmin only (`PUT /subscriptions/{id}/seats`, kept when the plan is replaced). Limit per role = included + extra (`_seat_limit`, `_check_seat_limit`): creating, activating or role-changing into a full role → 403 "Seat limit reached for this role" (also for the superadmin; no plan or no `included_seats` = no limit). There is no usage metering - extra accounts are contracted by hand and billed from the next charge. `GET /clients/{id}/seats` (superadmin) / `GET /clients/me/seats` (admin) → used/included/extra/limit per role + monthly total (package `prices["1"]` + extras − discount). `payments.kind` (`subscription`/`setup`/`other`), `period` (YYYY-MM), `breakdown`; monthly charges come from calendar billing drafts (below); setup fee = expected payment with `kind: "setup"` (a ledger charge, paid through the balance; does not extend the subscription). "Needs attention" (`/superadmin/overview`) also lists `setup_unpaid` (expected setup debt not yet late). The seat-limit error is translated in the portal (`lib/errors.ts` `localizedDetail`). Portal: plan dialog fields, client tab "Subscription" (accounts + edit), "Users" tab usage line, admin page `/seats` (`/api/my-seats`).
- **Units of measure** (plan: `.claude/DOCS/PLAN_JEDINICE_MERE.md`): global `units` collection (`code`, `name_sr/en`, `symbol`, `group` count/mass/volume/length/…, `base_code`, `factor`, `active`; `_id` = code), built-ins seeded at startup by `_seed_units` (kom, g, kg, t, ml, l, hl, mm, cm, m; never overwritten). `GET /units` (any user), `POST`/`PUT /units/{code}` (superadmin; group/base/factor locked while a product or another unit uses it, `kom` always locked). `products.unit` (missing = `kom`; `ProductInput.unit` None = keep; create default `kom`; changing it is 409 once the product has stock/movements/orders unless the new unit has the same `base_code`, e.g. m ↔ cm; packaging fields and package barcode only for `count` units). **Every quantity (stock, ordered/picked, batches, movements) is a whole number of the unit's BASE unit** (g, ml, mm, kom); the price is per the product's unit, so `calc.line_net` = `price × qty / unit_factor` (also `frontend/src/calc.ts`). `OrderItem` snapshots `unit`, `unit_symbol`, `unit_factor` (old orders = kom/1). Clients convert display ↔ base with the unit's `factor`. Portal `lib/units.ts` and mobile `src/utils/units.ts` (`useUnits` caches `GET /units`, `parseQty`/`formatQty`/`lineQtyLabel`/`cleanQtyInput`) do the conversion; portal page `/units` (superadmin), unit select on the product form (portal + mobile `admin.tsx`; packaging fields hidden for non-count units), quantities in the product's unit on stock, warehouse, catalog, invoice and delivery note; order lines use the snapshot (`unit_symbol`/`unit_factor`). Excel import column `Jedinica mere`, stock column is in that unit. Sales stats (`/stats/dashboard`, `/stats/overview`, `_compute_client_stats`) skip `canceled`/`rejected` orders and count shipped orders by `picked_qty` (same basis as the order totals); `top_products` rows carry `unit_symbol`/`unit_factor` (quantity in base units).
- **System settings** (plan: `.claude/DOCS/PLAN_NAPLATA_KALENDARSKA.md`, N1): one `app_settings` doc (`_id` "global") with business values the superadmin edits on the portal page `/settings` (`GET`/`PUT /settings`, superadmin; partial update, `null`/empty text = back to the default; audited as `settings.update`). `SETTINGS_DEFAULTS` holds the fallbacks (env, else code); read with `setting(key)` from a cache refreshed at most once a minute (`refresh_settings()`, called in `_client_gate`, `get_authenticated_user`, the cron and after a change). Keys: billing cycle (`draft_day` 25, `due_day` 1, `block_after_day` 5, `first_month_free`), `reminder_days` (was env `SUBSCRIPTION_REMINDER_DAYS`), `purge_after_days` (was `SUBSCRIPTION_PURGE_AFTER_DAYS`), default `expiry_alert_days`, payment details + IPS (`ips_account` normalized to 18 digits with a mod-97 check by `normalize_bank_account`), issuer data, billing sender / reply-to / `bilingual_emails`. Secrets, URLs, rate limits and `AUTO_PURGE_ENABLED` stay in env.
- **Calendar billing** (plan: `.claude/DOCS/PLAN_NAPLATA_KALENDARSKA.md`, N2 backend): every client with a plan is on it: `_enroll_calendar` runs on client create / plan assign (`cycle` monthly|annual → `subscription.billing_cycle`, end date aligned to the month end, optional 0 "Besplatan mesec" charge for the first partial month); the startup migration `_migrate_calendar_billing` moves older clients (monthly, annual if the plan has only a 12-month price; end date to its month end, never unlocks or shortens, no free month; idempotent). `POST /billing/clients/{id}/enroll` only changes the cycle. Only `payments` with `ledger: true` form the balance: drafts (`status: draft`, made by the cron from `draft_day` or `POST /billing/drafts/generate`, one per client + `period_start`; `lines` package / seats / seats_prorated / discount), approved with `POST /billing/drafts/approve` → `expected` + `number` `PR-YYYY-NNNN` (`counters` `proforma:{year}`) + `due_date` (`due_day` of the period month); charges never flip status. Payments: `POST /billing/payments` (FIFO over charges via `_allocate`, surplus = credit). `_apply_ledger` stores `subscription.balance_due/credit/open_charges/monthly_amount` and moves `ends_at` to the latest period with money (or 0) on it (never shortens). `subscription_state` for calendar clients: grace until `block_after_day` of the month after `ends_at` (or `due_extension_until`), plus `lock_reason` `manual` (`/subscriptions/{id}/block`, `/unblock`) or `debt` (after `block_after_day`, overdue open charges ≥ `monthly_amount`); those two never lead to a purge. Annual: 12 × extra accounts, accounts added mid-year → `annual_addon` draft for the remaining months (`extra_seats_billed`). `/payments/{id}/receive` refuses ledger charges. Client side (N3): `GET /billing/me` (client admin; charges with lines/number/open, `to_pay`, credit, payment instructions, IPS data) and `GET /billing/me/qr.png` (NBS IPS QR via `segno`, `_ips_string`: `K:PR|V:01|C:1|R|N|I:RSDx,yy|SF|S|RO:97…`; superadmin preview `GET /billing/clients/{id}/qr.png`); `/auth/me` carries `billing` (`next_due_date`, `late`, `blocks_on`, `lock_reason`; `to_pay`/`credit` for the admin only). A locked calendar-billing client: its admin can still log in and reach only `BLOCKED_ADMIN_PATHS` (`/auth/me`, `/auth/logout`, `/auth/change-password`, `/billing/me*`), elsewhere 403 "Subscription blocked"; other roles 403/401 "Subscription expired" as before. Portal page `/billing` (admin, "Zaduženja") + `SubscriptionBanner` (due / late / blocked; a blocked admin is redirected to `/billing`); mobile `TopBanners` billing notices and `BlockedScreen` (RouteGuard), `setBlockedHandler` re-reads `/auth/me` on a 403 "Subscription blocked". Superadmin portal (N5): page `/billing-drafts` (drafts: generate now, edit amount/note, free month, drop = `/payments/{id}/cancel`, approve selected/all) and client tab "Naplata" (`components/BillingPanel.tsx`: change cycle, balance, charges via `components/ChargeLines.tsx`, ledger payment, extend due, block/unblock, QR preview); "Zaduži mesec" / "Uplata i produženje" are gone. Mobile: one alert per sign-in for the admin (amount, due date, details on the portal). Attention: `drafts_pending`, `debt_repeated` (≥ 2 late open charges), `blocked_debt`; the end-date reminder skips monthly clients. Billing emails (N4): HTML + text (`_compose`, Serbian + English when `bilingual_emails`), IPS QR as an inline image (`cid:ips-qr`), sender / reply-to from the settings (fallback `SMTP_FROM`); recipients = active client admins + `clients.accounting_email`, each address once (`_billing_recipients`). Events: `issued` (on approval or a manual debt; 0-din charges skipped), `reminder` (on/after the due date), `warning` (2 days before the block, only if `subscription_state` on the block day says locked), `blocked` (once per block, `subscription.block_notified`), `paid` (only with `send_receipt` on `POST /billing/payments`), `annual_expiry` (annual clients, ignores the opt-out), `drafts_ready` (to superadmins when the cron makes drafts). `subscription.billing_emails: false` = opt-out (banners stay). Every email is logged in `billing_emails` (`sent`, `skipped` disabled / no_recipients / smtp_off, `text`) and charge emails set `notified.<event>` on the charge, so the cron never repeats one; reminders run in the cron (`_billing_notifications`; `as_of` query param outside production for tests). `GET`/`PUT /billing/clients/{id}/emails` (superadmin: switch, accounting address, recipients, log); portal "Naplata" tab card "Emailovi za naplatu" and the receipt checkbox in the payment dialog.
- **Goods in focus** (module `focus`, plan: `.claude/DOCS/PLAN_FOKUS_I_CILJEVI.md`): `focus_items` (`product_id` unique per client, `reason` stock/expiry/promo/other, `note`, `recommended_discount` = one of the product's `additional_discounts` because the rep picks the additional one, `active_to`). `GET/POST /focus`, `PUT/DELETE /focus/{id}` (admin; superadmin needs `client_id`); `GET /focus` also returns `suggestions` (stock cover ≥ 90 days or no sales in 30 days; batches close to expiry). `GET /products` adds `focus` (`FocusInfo`) for active focus items of inactive-excluded products; the expiry date/qty is shown to sales reps ONLY for focus items with reason `expiry` (the one exception to "reps never see expiry data"). Order lines snapshot `focus: bool` (for the `focus_revenue` target and the report). `GET /focus/report` (manager; `from_date`/`to_date`, default this month): sales of focus lines (not canceled/rejected, shipped by `picked_qty`) per product and per sales rep, shown under the list on the portal `/focus`. Portal `/focus` (+ `ModuleGate`), mobile catalog: highlighted card, "Fokus" chip, focus items first, "Primeni" sets the recommended additional discount, soft hint on confirm when no focus item is in the order.
- **Sales targets** (module `targets`): `targets` (`user_id` = sales rep, `period_type` month/quarter/year, `period` `2026-03`/`2026-Q1`/`2026`, `metric`, `value`; unique per combination). Metrics `TARGET_METRICS`: `revenue` (net RSD), `orders`, `customers` (distinct), `focus_revenue` (lines with the order-line `focus` snapshot). Progress is never stored: `_target_achieved` computes it from `orders` (not canceled/rejected, shipped by `picked_qty`, `created_by_user_id`, period by `created_at` in UTC). `PUT /targets` (set, `null`/0 removes), `POST /targets/copy` (fills only what is missing), `GET /targets/progress` (manager; every active sales rep with targets, achieved, pct and `previous_year` = same period a year earlier), `GET /targets/me` (sales rep only: current month, `days_left`, `daily_needed`, `projection`, 3 months of history - never quarter/year and never other reps). Portal `/targets` (period switch, copy previous, "suggest = last year + X%", per-rep editing) and mobile tab "Moj učinak" (`app/(tabs)/progress.tsx`, operators with the module).
- **Stock (minimal):** `products.stock_qty` (pieces; `null` = untracked) is never written by product PUT (`update_product` excludes it) — only by `POST /stock/receipts`, `POST /stock/adjustments` (counted qty, note required) and shipping. Every change is an append-only `stock_movements` doc (`receipt`/`adjustment`/`shipment`/`reversal`), listed by `GET /stock/movements` (`require_stock_writer` = superadmin/admin/warehouse). Moving an order to `shipped` deducts `picked_qty` (negative stock allowed); leaving `shipped` (admin override) restores it. `GET /products` adds `reserved_qty` (sum of `ordered_qty` in `new`+`in_progress` orders) and `available_qty` = stock − reserved. Portal page `/stock`; mobile catalog shows on hand/available and warns (no block) when the qty exceeds it. Plan: `.claude/DOCS/PLAN_STANJE_MAGACINA.md`.
- **Barcodes & import:** `products.barcode` (one code per piece, `[A-Za-z0-9-]` max 32, unique per client via partial index + explicit 409; `ProductInput.barcode` None = keep, `""` = clear). `products.package_barcode` = barcode of one box (`pieces_per_package` pieces; same rules, needs `pieces_per_package` > 0, 400 otherwise): a code is unique across both fields per client and must differ within one product (`_checked_barcode`, `_require_package_size`). `GET /products/by-barcode/{code}` (scoped, returns stock fields plus `scan_unit` `piece|package` and `scan_qty` = pieces one scan stands for), `POST /products/{id}/barcode` (`kind` `piece|package`; warehouse can link a scanned code), `POST /products/quick` takes `barcode_kind`. Mobile `StockScanPanel`: a scanned box adds `scan_qty` pieces at once (receipt/count); for products with expiry tracking the date is still required on receipt (a count may use the undated row). Excel import column `Barkod kutije`. `POST /stock/adjustments/batch` = a whole stocktake in one request (all products validated first). `POST /products/import` (manager, `.xlsx`, `dry_run=true` default → per-row create/update/error, `client_id` for superadmin) matches by barcode then exact name, empty cell keeps the stored value, `stock_qty` column becomes an `adjustment` movement (note "Uvoz iz Excela"); `GET /products/import-template` (downloads a valid 9-row example incl. a product sold by kg; column `Jedinica mere` = unit code or name, the stock column is in that unit); needs `openpyxl` (in requirements.txt). Customers have the same flow: `POST /customers/import` (match by PIB, else exact name; empty cell keeps value; email lowercased; PIB digits only) + `GET /customers/import-template`; portal `components/ImportModal.tsx` serves both pages (`kind` prop). Example files: `.claude/DOCS/primer-uvoz-artikala.xlsx`, `primer-uvoz-kupaca.xlsx`. Plan: `.claude/DOCS/PLAN_BARKOD_I_MOBILNI_MAGACIN.md`.
- **Money math:** `backend/calc.py` is the source of truth. `frontend/src/calc.ts` duplicates it for the unsaved-order preview and the invoice — keep both in sync. admin-web has no copy (uses `totals`/`line_net`).
- **Product images:** `/upload-image` accepts JPEG/PNG/WEBP/HEIC up to 4 MB (Vercel's body limit is 4.5 MB), Cloudinary stores it shrunk (max 1000px, WEBP). Replaced/deleted product images are removed from Cloudinary (`_delete_product_image`), only for URLs in the `easy-order/products` folder. Forms upload the image only on "Save" (a local preview until then); if the product write fails afterwards the client calls `DELETE /upload-image?url=` (manager; own folder only, 409 if a product uses it). `backend/scripts/cleanup_orphan_images.py` removes old orphans (dry run by default, `--apply` to delete).
- **Production guard:** `IS_PRODUCTION` = `APP_ENV=production` or `VERCEL_ENV` production/preview. There, a missing `JWT_SECRET` stops startup, and the default superadmin password is refused. Demo data is seeded only with `SEED_DEMO_DATA=true` and never in production.
- **Mobile app distribution:** `GET /api/app/update` serves `backend/public/app/app-update.json` (`version`, `download_url`, `build_date`, `release_notes`). APKs are GitHub Releases, never committed (`*.apk` is gitignored); `download_url` is the versioned release URL. Releases go through `.github/workflows/release-android.yml` (sets `app.json` version, EAS build, GitHub Release, updates the JSON); JS-only changes through `ota-update.yml` (EAS Update, channel `production`, `runtimeVersion` policy `fingerprint`). Don't bump `app.json` `version` by hand and don't run `eas update` locally (it would inline the local `.env` backend URL). Details: `.claude/DOCS/IZDANJE_APLIKACIJE.md`.

- **Delisting & quick add:** `products.active` (missing = active; `ProductInput.active` None = keep) is edited by managers (portal checkbox, mobile Switch in `admin.tsx`). Operators' `GET /products` omits inactive ones, `_resolve_order_lines` rejects them (400), activating a product with price ≤ 0 is 400. `POST /products/quick` (`require_stock_writer`; name, barcode, optional manufacturer/packaging) creates an inactive, price-0 product so the warehouse can add an unknown scanned item (mobile `StockScanPanel` unknown-barcode modal → "Dodaj novi artikal"); an admin then sets price/VAT and activates it. Inactive products are still found by barcode and can be received/counted.

- **Expiry tracking:** `products.track_expiry` (manager toggle in portal/mobile product form; also the "Prati rok (da/ne)" import column) keeps that product's stock in `stock_batches` (`product_id`, `expiry_date` YYYY-MM-DD or null = undated, `qty`; unique per product+date, created by upserts in `_batch_inc`); `stock_qty` stays the sum of the batches, so reservations/catalog work unchanged. All stock changes go through `_apply_delta` (stock + batch + `stock_movements` row with `batch_id`/`expiry_date`). Receipts need `expiry_date` for tracked products; counts send `batches` (`[{expiry_date, counted_qty}]`, unlisted batches go to 0) instead of `counted_qty` (plain counts/Excel import land on the undated batch). Shipping takes the warehouse's `picked_batches` (PATCH `/orders/{id}/items` with `batches`) or FEFO (`_fefo_plan`: undated first, then earliest expiry, never expired; shortfall goes negative on undated) and stores the result on the order line; reversal restores the same batches. Switching tracking on turns existing stock into an undated batch; off is 409 while dated batches hold pieces. Expired pieces are excluded from `available_qty`. `GET /stock/expiring` (admin + warehouse only, 403 for superadmin/operator) returns batches that are expired or within the client's `expiry_alert_days` (default 5/15/30, edited by the superadmin in the client form); `POST /stock/batches/{id}/writeoff`, `GET /products/{id}/batches` for the warehouse/admin. Sales reps never see expiry data (`_product_out`, `_without_batches` strip it). UI: portal `/stock` (banner, receipt date, per-date count, write-off), mobile Magacin "Rokovi" tab + `ExpiryCard` in `StockScanPanel` (dates typed DD.MM.GGGG, `src/utils/expiry.ts`). Plan: `.claude/DOCS/PLAN_ROK_TRAJANJA.md`.

When adding a product field: add it to `Product`, `ProductInput`, `OrderItem` and the snapshot in `create_order`, then to `frontend/src/api.ts` and the catalog → invoice flow.

### Admin portal (`admin-web/`)
- `proxy.ts` (Next 16's name for middleware) verifies the session cookie (JWT, same secret as the backend) and redirects; operators are refused and warehouse users are limited to the paths in `lib/session.ts` (`isPathAllowed`/`homePath`). In production without `JWT_SECRET` every session is rejected.
- `app/api/**/route.ts` proxy to FastAPI through `lib/backend.ts` (`backendFetch` adds the Bearer token from the httpOnly cookie). `api/auth/login` and `api/auth/change-password` set the cookie.
- `app/(dashboard)/layout.tsx` loads `/auth/me` and redirects to `/change-password?required=1` while `must_change_password` is set.
- `app/(dashboard)/warehouse` (packing queue, status actions, delivery note), `stock` (stock levels, receipt, count, history), `products` (barcode field, Excel import via `components/ProductImportModal.tsx`), `orders` (status/date filters, invoice + delivery note print via `components/OrderPrintModal.tsx`), `clients/[clientId]` (superadmin edits company + invoice settings + logo).
- The App downloads page reads the backend's `/api/app/update` server-side (single source of truth with the mobile update prompt).
- Strings go in `lib/i18n.tsx` (`sr` and `en`).
- Form inputs get a visible label above them (`components/FormField.tsx`: `Field`, `FieldGroup`, `fieldInput`), not just a placeholder - a placeholder disappears once the field has a value.
- **Phones / PWA:** the portal on a phone is for the superadmin only: below `md` every other role gets `components/DesktopOnlyNotice.tsx` ("computer or the Android app", logout) instead of the dashboard layout (`app/(dashboard)/layout.tsx`, CSS only; login / password pages stay usable). Below `md` (768px) `Sidebar` is a drawer behind a ☰ top bar and `main` has `p-4`; desktop is unchanged. Installable: `app/manifest.ts` (standalone, theme `#1A4D2E`) + `public/icons/` (from the mobile app icon), both excluded from the `proxy.ts` matcher; no service worker (data must be live). Tables with class `rtable` (globals.css) turn into one card per row below `md`: the first cell is the title, `<td data-label={t(...)}>` shows as "label ... value", cells without a label (actions) stay full width - used on all superadmin pages; client-admin / warehouse pages are desktop-only and were not reworked. `PaymentsPanel` has its own cards below `md`; client tabs scroll sideways. Form fields are 16px on phones (globals.css) so browsers don't zoom. New superadmin pages: keep them usable at 360-400px.

### Command guard (`frontend/scripts/cmd-guard*`)
`npm install` runs `scripts/cmd-guard.js --preinstall`; it can allow/block/rewrite commands (exit 0/1/2). If an install/dev command fails or gets rewritten unexpectedly, check `scripts/cmd-guard/rules.js` first.
